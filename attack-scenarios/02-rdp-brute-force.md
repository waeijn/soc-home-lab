# RDP Brute Force

## Overview
An attempt to guess the password of a valid user account by rapidly and repeatedly authenticating against the Remote Desktop Protocol (RDP) service using a dictionary of common passwords. This simulates an adversary attempting to gain initial access or escalate privileges via Credential Access.

## MITRE ATT&CK
- **Tactic:** Credential Access
- **Technique ID:** T1110.001
- **Technique Name:** Brute Force: Password Guessing

## Tools Used
- Hydra

## Target
- Machine: win-target (192.168.56.101)
- Service/Port attacked: RDP (TCP 3389)

## Attack Execution
### Command Used
```bash
hydra -l analyst -P /usr/share/wordlists/rockyou.txt rdp://192.168.56.101
```

### What It Does
Uses the Hydra network logon cracker alongside the standard `rockyou.txt` wordlist to automate login attempts against the Windows target machine over RDP, targeting the local user `analyst`.

## Telemetry Generated
| Event ID | Source | Description |
|---|---|---|
| 4625 | WinEventLog:Security | An account failed to log on. A massive spike in these events indicates brute force activity. |
| 4624 | WinEventLog:Security | An account was successfully logged on. Important to track to see if the brute force was successful. |

## Detection SPL

```spl
index=main sourcetype=WinEventLog:Security (EventCode=4625 OR EventCode=4624)
| eval event_type=if(EventCode=4625, "FAILURE", "SUCCESS")
| bucket _time span=60s
| stats count(eval(event_type="FAILURE")) as failures, 
        count(eval(event_type="SUCCESS")) as successes 
        by _time, Source_Network_Address, Account_Name
| where failures > 5
```

## Notes
The detection query uses `bucket _time span=60s` to look for more than 5 failed logon attempts within a 1-minute window from a single source address. By including Event ID 4624, the query can also highlight if the attack eventually resulted in a successful logon (`successes > 0`).

### Technical Deep Dive: Why 4625 Events Can Be Hard to Generate

During testing, we encountered issues reliably generating Event ID 4625 ("An account failed to log on") using modern tools against Windows 10. 

**What EventCode 4625 Actually Is**
It is generated by the Windows Local Security Authority (LSA) when an authentication attempt fails through specific channels that Windows monitors.

**Why RDP Brute Force with Hydra Doesn't Always Generate 4625**
- **With NLA Disabled:** RDP authentication happens inside the RDP protocol layer itself, not through Windows' standard authentication pipeline. The connection is established first, then credentials are checked at a layer Windows Security auditing doesn't fully see. Hydra exploits this gap — it connects, fails, disconnects, and Windows never writes a 4625.
- **With NLA Enabled:** Hydra can't even complete the handshake because NLA requires valid credentials before the RDP session is established. Hydra gets connection errors and no authentication attempt reaches Windows at all. (This is why modern security guides recommend keeping NLA enabled — it breaks most RDP brute force tools entirely).

**Troubleshooting Steps Taken:**
| Attempt | What We Tried | Result |
|---|---|---|
| 1 | Hydra `-t 1 -W 3` with NLA disabled | Connected and cracked but no 4625 events |
| 2 | Hydra `-t 1` no wait with NLA disabled | Same — cracked but no 4625 |
| 3 | `ncrack` against RDP | Ran for minutes, no results |
| 4 | `crowbar` installed from GitHub | No results found |
| 5 | Re-enabled NLA, ran Hydra | Hydra connection errors, no 4625 |
| 6 | SMB authentication via `net use` from Kali | No 4625 events generated |
| 7 | Local PowerShell credential attempt on Windows | No 4625 events generated |

**Root Cause**
Modern Windows 10 is specifically hardened against generating these events through tool-based RDP attacks. Hydra's RDP module is experimental and bypasses proper auth logging. The historic 4625 events captured in our dataset were likely generated by `ncrack` running for several minutes and happening to hit the right authentication layer, but it is too slow and inconsistent to reliably reproduce on demand.
